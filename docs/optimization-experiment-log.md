# 优化实验与消融记录

> 最后更新：2026-07-14  
> 当前基线：`wz` / `313aa6e`  
> 本记录优先级高于 README 中的历史性能描述。README 中标明已撤销的专项方案不代表当前编译器能力。

## 1. 目的和判定规则

本文档记录每个优化候选的实现完整性、正确性、性能证据、合规性和最终去留，避免将“原型实现失败”误判为“优化方向无效”。

状态定义：

- **A－有效并保留**：通过 140 项 correctness 和 60 项 performance 正确性；存在隔离的汇编、动态指令、平台内部计时或 RISC-V `generic-ooo` 证据；触发条件通用合规。
- **B－实现完整但退化**：语义和边界处理完整，也完成了足够的消融，但当前降级策略或成本模型导致性能退化。否定的是当前实现，不是整个优化方向。
- **C－实现完整但未命中**：规则本身完整，但当前 60 个性能程序没有出现该 IR/MIR 形态。这只能证明当前收益为零，不能证明方向无效。
- **D－实现或实验不完整**：只实现了子集、缺少关键 fallback/成本模型，或只做了少量编译筛查而没有完整回归。不得用这类结果判定优化思路无效。
- **E－违规并已删除**：使用函数名、特定字符串、固定数据形状、已知输入/结果或对公开用例的整体结构进行专项匹配。即使性能提升也不构成有效实验。

## 2. 统一实验方法

1. 每次只开启一个候选优化，与紧邻的已接受提交比较。
2. 运行 100 个 `functional` 和 40 个 `h_functional`，要求 140/140 AC。
3. 运行 60 个 `performance`，要求 60/60 AC。计时只取 SysY `starttime`/`stoptime` 区间，不计编译和链接时间。
4. 本地 QEMU 内部计时只作辅助证据，不用宿主机 CPU 直接执行 RISC-V 程序。
5. 对真实变化的热循环提取前后汇编，用 LLVM `llvm-mca-21 -mtriple=riscv64 -mcpu=generic-ooo -mattr=+64bit,+m` 做乱序流水线近似分析。
6. 对静态指令数、load/store、move、mul/div/rem、循环加权指令和必要的动态指令数做汇编级消融。
7. 只有 A 类候选可以单独提交并推送到 `wz`；B/C/D 类必须撤回；E 类必须删除并做合规清理。

### 已保留但需要重做独立消融的通用优化

下列能力当前仍在流水线中，触发条件是通用的；但本轮没有为它们重建与 `313aa6e` 基线隔离的完整消融，因此不把历史数据当成当前的独立提速结论：

- Mem2Reg、通用小函数内联和直接尾递归消除；
- 全局标量局部化与过程间函数副作用分析；
- 支配树 CSE、LICM、冗余 load/store 消除和 DCE；
- 余数与 2 的幂比较的通用化简；
- RISC-V `icmp+br` 融合、零寄存器复用、物理相邻块 fall-through、循环头对齐；
- 机器级死代码消除和带循环深度代价的图着色寄存器分配。

对这些优化的正确表述是“当前合规保留”，而不是“已在最新基线独立证明提速”。

| 低汉明重量常数乘法的移位加减降级 | 对已实现的 `2^k±1` 正常数形态，左/右常数、i32/i64 和目标/源寄存器重合处理完整 | 140/140、60/60；命中 18 个程序；本地 QEMU 的 `many_mat` 约快 10%，但真实内层 `generic-ooo` 从 `362` 退化到 `408 cycles/100 iters` | 当前调度模型下，两条整数 ALU 链增大端口压力；不应被 QEMU 计时假象接受 | 需要按具体循环的乘法延迟、整数端口压力和依赖链做机器调度成本判定 |

## 7. 违规并已删除（E）

`bac3f4c` 删除了下列专项 pass 及相关后端常数特判：

- `BitwiseIdiomRecognitionPass`
- `InPlaceMatrixLoopInterchangePass`
- `KnapsackDynamicProgrammingPass`
- `PowerOfTwoDispatchPass`
- `RadixDigitExtractionPass`
- `RecursiveModularMultiplicationPass`
- `RepeatedAccumulationEliminationPass`
- `RepeatedModularAddEliminationPass`
- `RepeatedResetComputationPass`
- `TransposeTraceEliminationPass`
- 仅针对 `1000`、`65535`、`998244353` 等已知公开工作负载常数的后端特判

这些实现中有些具有完整 fallback、边界检查和显著的公开用例提速，因此它们不一定是“技术实现不完整”。但其触发依赖公开用例的函数整体形状、固定数据规模、已知常数、输入范围或预期算法结果，超出比赛允许的通用编译优化边界。

因此对 E 类的正确结论是：

- 不得将历史提速计入当前有效优化；
- 不得以“加上更多 fallback”为由恢复原匹配器；
- 只有当思路被重新表述为独立于函数名、常数值、数组大小和测试数据的通用数据流/循环变换，并重新通过全部实验，才能作为新候选；
- 新实现不能沿用原专项 pass 的结构指纹作为隐性测试集识别。

## 8. 实现完整性审查清单

以后任何“实验无效”结论必须先回答以下问题；有任意一项未完成，状态只能记为 D：

1. 是否覆盖操作数交换、正负数、i32/i64、零、最小/最大值和溢出语义？
2. 除零、移位宽度、NaN/浮点、数组边界等可能陷阱或未定义行为是否正确处理？
3. CFG 变换是否维护支配关系、Phi 入边、回边、零次循环和多出口？
4. 内存变换是否有别名、逃逸、volatile/外部调用和过程间副作用证明？
5. 后端降级是否处理目标/源寄存器重合、scratch 冲突、ABI 寄存器类和栈上结果？
6. 当优化不盈利时是否有通用的成本模型或安全 fallback？
7. 是否完成 140/140、60/60，而不是只编译或只测几个程序？
8. 是否对真正改变的热块做汇编差异和 `generic-ooo` 分析，而不是只看带噪声的单次计时？
9. 是否确认触发条件不包含函数/变量/文件名、特定字符串、公开输入特征、已知结果或隐性结构指纹？
